# 提示词生成质量：下一阶段候选

基线为 v1.1.1。本阶段先建立质量基线和对照方法，尚未改动生成规则；严格模板、JSON 协议、安装器或运行时均不变。以下是评估方法及待执行案例，尚未证明宿主输出质量提高。

## 先判断保真，再比较好不好用

任何一项阻断问题都不能用文风评分抵消：丢失或改变明确约束、虚构事实或授权、错误合并/撤销、跨任务污染，以及无执行证据却宣称严格成功。篇幅要求同时检查数字、单位、限制强度和约束对象；只数提示词长度不能判断目标结果篇幅要求是否正确。

保真通过后，按以下维度比较同一输入的两个输出，每项记录 0/1/2 及对应原文。0 表示明显问题，1 表示可用但可改进，2 表示满足本项。证据不足记录未知，不填写分数。

| 维度 | 0 / 1 / 2 的区别 |
| --- | --- |
| 清晰与可执行 | 关键交付不明 / 可理解但有局部冗余或顺序问题 / 任务和必要条件清楚 |
| 领域适配 | 套入不适用流程 / 基本合适但有无用章节 / 根据实际交付组织 |
| 信息密度 | 重复堆砌或大量无关要求 / 有少量重复 / 每条文字都有保留约束或消除歧义的作用 |
| 澄清成本 | 重问已给信息或不解冲突 / 问题有用但可合并 / 只问影响交付的缺口，完整输入直接生成 |
| 复制与修订 | 输出难复制或无法正确局部修改 / 可复制但夹杂说明 / 正文独立，修订保留未改要求 |

不按总分自动判定上线；同一输入中，候选不得引入新的阻断问题，优先比较预定目标维度，其余维度不得明显退步。提示词变短但删了约束属于失败；更长但每项确有必要，可以优于较短版本。

## 小规模对照流程

1. 在同一宿主、可见模型设置和工具条件下，分别加载 v1.1.1 与本地候选；按[来源验收](chatgpt-acceptance.md)记录加载证据，不能只依赖模型自述。
2. 使用[质量样例](../tests/fixtures/prompt-quality.json)，每个任务新聊天；多轮修订保持在同一聊天。只给 input，不提供质量预期。已有完整回归仍使用[对话用例](conversation-regression.md)。
3. 保留全部输入、完整输出、澄清轮次及工具记录。先审阻断项，再隐藏版本标签比较 A/B；另一轮互换展示顺序，允许判定相当。
4. 首轮逐项人工复核，优先 Q01/Q03/Q05；其余案例用于检查复杂任务没有因简洁性规则漏项。受改动影响的场景在新聊天重复两次。失败轮次也保留，不能只挑最佳输出。
5. 记录基线提交、候选 diff、日期、宿主/模式、模型标识、来源证据、案例与轮次、阻断结论、各维度理由和 A/B 偏好。合成结果可脱敏公开，原始账号/会话记录只存私有目录。

单元测试证明程序行为，JSON 解析证明用例格式，人工示例证明评分含义；它们都不替代真实宿主生成。没有已核实模型 API 依赖，暂不引入评判服务或自动打分框架。日后接入自动评判前，先核对其判断与人工记录的一致性。

## 校准示例（合成示范，不是执行结果）

输入：给 ChatGPT 写中文欢迎信，300 字左右，亲切，不写公司历史，不编造福利；只整理提示词。

- 可用的短草案：请写一封约 300 字的中文欢迎信，语气亲切。不写公司历史，不虚构福利或公司承诺；未提供的姓名与落款使用占位符。
- 无效的短草案：请写一封中文欢迎信。它省掉了篇幅与内容限制，保真不通过。
- 需要删减的长草案：保留以上要求，却另加“核对公司沿革、制定审批流程、形成实施和回滚计划”。这些内容不服务写作任务，且核对沿革偏离“不写公司历史”，不能因为结构完整而评为更好。

参考：[OpenAI 的评估方法](https://developers.openai.com/api/docs/guides/evaluation-best-practices)建议使用任务对应的样例与标准、结合人工判断，并注意比较中的顺序及篇幅偏好。本项目不采用该页面示例应用的数值阈值，也不因此依赖 Evals API。
