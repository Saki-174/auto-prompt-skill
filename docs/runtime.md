# 运行逻辑与模型分工

[返回首页](../README.md#运行逻辑) · [安装教程](install.md) · [输入协议](../skills/auto-prompt/references/input.md)

Auto Prompt 是“技能说明＋参考材料＋可选严格脚本”。宿主加载这些资源，当前模型按技能规则处理需求；插件没有自己的生成模型，不调用 Ollama 或其他模型 API。安装器负责准备文件、登记与运行依赖，只解决可执行条件，不承担需求理解。

## 从调用到输出

1. **加载技能。** 在已启用 Auto Prompt 的聊天中调用技能，宿主提供技能说明和可访问资源。仅看到同名插件条目，不能证明实际执行文件来自该条目。
2. **读取输入。** 当前模型读取目标 Agent、原始需求、模式与约束；已提供的信息直接复用。只调用技能而没有需求时，先询问缺少的目标或任务，不运行空模板。
3. **按需澄清。** 只有会改变目标、范围、交付物或验收方式的歧义才追问；非关键缺失可以标为待确认后继续。完整输入可直接进入生成。提示框依赖宿主实际提供的输入工具，工具不可用时使用文字问题。
4. **按模式生成。** 灵活模式由当前模型理解和改写；严格模式核验原执行文件与运行条件后，调用原脚本校验 JSON、选择模板并固定渲染。
5. **交付与修订。** 返回可复制的提示词。追加、替换或撤销由当前模型结合可见对话处理；切换新任务时，技能要求清除上一任务的目标与约束。这些是对话规则，不是独立的状态数据库或程序化撤销引擎。

生成结果只是待交给目标 Agent 的任务说明。说“直接使用”结束转换，不自动执行其中的开发、部署、发消息或内容生成任务。

## 各部分负责什么

| 环节 | 模型与宿主的职责 | 插件提供的内容与程序 |
| --- | --- | --- |
| 需求理解与引导 | 理解口语、复用上下文、选择必要问题 | `SKILL.md` 的接收、引导与歧义规则 |
| 灵活生成 | 按任务与目标 Agent 组织内容，核对原意与约束 | 领域说明、约束保真及输出规则；没有独立的语义评分程序 |
| 严格执行前 | 判断模板冲突，确认文件来源，使用可用执行工具 | 输入协议、原脚本、运行时维护策略与 Windows 启动器 |
| 严格渲染 | 提供执行环境；自然语言输入时整理 JSON | 脚本检查字段、类型与长度，按既有规则选取四套中英文开发／通用模板并替换占位内容 |
| 生成后修改 | 结合可见对话追加、替换、撤销或开始新任务 | 修订和任务隔离规则；不自动写入长期记忆 |
| 安装与升级 | 提供安装、登录、授权和启用入口 | 文件安装、依赖检查、专属运行时准备、备份与恢复；这些不直接提高生成内容的语义质量 |

主要实现入口：[技能规则](../skills/auto-prompt/SKILL.md)、[对话规则](../skills/auto-prompt/references/conversation.md)、[渲染器](../skills/auto-prompt/scripts/render_prompt.py)、[运行时策略](../skills/auto-prompt/scripts/runtime_policy.py)、[Windows 严格启动器](../skills/auto-prompt/scripts/Run-Strict.ps1)。

## 输入与严格模式的边界

- 自然语言需求未指定模式时，默认灵活模式。
- 完整任务 JSON 沿用兼容协议：`strictMode` 缺省按 `true`，显式 `false` 走灵活模式；直接渲染 CLI 保持严格默认。
- 自然语言选择严格模式时，当前模型仍需将原需求和约束整理为 JSON。这一步可能随模型或对话变化，不属于确定性保证。
- 渲染器按既有规则清理字段、补充缺省约束，并根据 `profile` 和 `requirements` 中的语言关键词选择模板；它不进行语义理解，也不从目标 Agent 名称推断专有格式。字段、默认值与语言限制见[输入协议](../skills/auto-prompt/references/input.md)。
- 严格执行必须使用来源可核验的原脚本和模板。宿主直接执行 Python 时，先检查运行时策略，通过后用同一解释器运行渲染器；Windows 启动器已有对应检查，并读取本机登记的专属运行时。
- 缺少工具、原文件或合规运行时时，说明“未运行严格模板脚本，无法提供严格结果”，保留输入，提供恢复入口或灵活模式选择；不模拟成功、不放宽策略。网页环境与本机环境分别检查，本机准备成功不代表云端运行时已满足条件。
- 已发现语言判定或固定章节与要求冲突时，由当前模型先澄清；直接 CLI 不进行这项语义判断。明确接受已说明的限制后，按原 JSON 执行。

确定性保证是：**固定脚本、固定模板和相同 JSON，得到相同 UTF-8 输出。** 原样返回脚本结果，不再由模型润色。它不保证任意需求都能被正确理解，不自动翻译，也不自动消解矛盾或适配所有 Agent 的专有参数。直接 CLI 可以在不调用生成模型的情况下渲染已有 JSON。

## 当前模型与目标 Agent

**当前模型**运行技能并生成提示词；**目标 Agent**是随后接收提示词的工具或模型。两者可以相同，也可以不同。

例如，在 ChatGPT 中要求“给 Codex：只修改 parser.py”，是让当前 ChatGPT 模型组织一段适合 Codex 的任务说明。Auto Prompt 不会因此切换为 Codex 模型、访问目标项目或执行修复。最终任务能否完成，还取决于目标 Agent 的模型能力、可用工具、上下文及权限。

## 对提示词质量的影响

灵活模式依赖当前模型完成语义工作。技能提供可复用的方法与限制，有助于提醒模型保留数量、单位、对象、禁止事项和修订范围，但规则是否被正确执行仍需要检查。技能不会修改模型的训练权重，也不能保证消除遗漏或幻觉。

模型类型和版本可能影响复杂需求理解、长约束保留、冲突判断与多轮修订。输入越不完整、任务越复杂，这些差异越值得单独验证；这并不是本项目已测得的跨模型排名。OpenAI 也说明不同模型类型和快照可能产生不同响应，建议通过评测检查表现。[官方提示词说明](https://developers.openai.com/api/docs/guides/prompt-engineering)

不能把质量写成“模型占 80%、插件占 20%”之类的固定比例：目前没有可支持该归因的数据，而且规则、模型、输入与上下文会互相影响。

| 场景 | 可以判断的影响边界 |
| --- | --- |
| 口语需求的灵活改写 | 模型承担理解和写作，技能约束处理方法；两者共同影响质量 |
| 自然语言转严格 JSON | 模型影响字段抽取，脚本只处理实际收到的 JSON |
| 已有相同 JSON 的严格渲染 | 输出由固定脚本与模板决定；宿主模型不参与最终文字改写 |
| 生成提示词交给目标 Agent 执行 | 还受目标模型、工具与执行条件影响，不能只归因于 Auto Prompt |

严格结果一致不等于语义质量更高；灵活模式能适配任务，也不等于每次都保真。两种模式需要分别验收。

## 如何验证效果

先检查项目的[验证范围](validation.md)与[对话回归用例](conversation-regression.md)，区分脚本测试、实际对话与尚未验证的能力。自动测试不能代替真实宿主中的需求理解、澄清和修订验收。

若要评估技能增益，使用相同原始需求、相同模型和相近上下文，对照“启用技能”与“不启用技能”；若要评估模型差异，则固定技能版本、输入和任务。对照时检查原意、数字与限制、未经确认的新增要求、必要追问、跨任务污染及复制使用的便利程度。多次运行并人工核对后再下结论，不把单次主观体验换算为质量百分比。

技能加载的一般机制参见 [OpenAI skills 文档](https://developers.openai.com/plugins/concepts/skills)。这份说明描述项目实现与职责边界，不表示所有网页、移动端、客户端或模型组合都已验证。
